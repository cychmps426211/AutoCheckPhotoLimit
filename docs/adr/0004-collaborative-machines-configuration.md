# 0004. 採用獨立設定檔管理跨維修師協同機台與預設查詢合併策略

## 背景與問題
現場維修師（預設維修師 `uno = 91`）平時巡檢與更換底片的責任範圍，包含其他維修師名下的特定機台（例如 `uno = 19` 位於高雄區域的 24 台機台）。
然而，這些機台在後台系統的名單中並不一定包含「高雄」等字眼，無法僅依名稱規則篩選。
若將大量機台代號寫死在程式碼中或透過環境變數傳遞，會造成維護困難且容易因換行/引號格式出錯。

## 決策
1. **設定與邏輯分離**：建立獨立設定檔 `config/collaborative_machines.json`，集中維護協同維修師編號（如 `uno: 19`）及其關注的機台清單（包含 `id` 與 `name`）。同時支援透過 `COLLABORATIVE_CONFIG_PATH` 環境變數自訂路徑。
2. **預設查詢合併機制**：
   - 僅在維修師發送「預設查詢」（「底片」、「檢查底片」）或「預設門檻查詢」（「底片 < 20」）時，系統自動載入協同機台設定，並對後台發送請求。
   - 依設定檔中的機台代號清單進行精確篩選，並套用相同之狀態或張數門檻過濾。
   - 與主維修師機台合併、去重後，統一執行「緊急排序」（剩餘張數由少至多升冪排列）。
3. **指定維修師隔離**：當使用者明確指定查詢特定維修師時（如「底片 師 88」），保持單一維修師查詢行為，不混合協同機台。
4. **容錯與平滑降級**：協同機台查詢若發生後台超時或設定檔異常，僅記錄警告日誌並略過協同機台，不中斷主維修師機台之查詢與回覆。

## 影響與後果
- 維運人員若需調整負責機台（新增、撤點、轉移），僅需編輯 JSON 設定檔即可生效，完全不需改動 Python 程式碼。
- 現場維修師發送「底片」指令即可一覽名下 91 及支援 19 的所有缺紙機台，大幅提升巡檢補紙效率。
- 設定檔隨 Git 版本庫統一管控，相容 Render 容器化部署環境。
